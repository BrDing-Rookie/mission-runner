# 文件锁机制（并发安全）

> 模块: file-system
> 创建日期: 2026-04-06
> 状态: 进行中
> 关联 Phase: P2

## 目标

为 Mission Runner 添加基于 lockfile 的排他锁，防止多个 watchdog 并发操作同一 mission 时的 TOCTOU（Time-Of-Check-Time-Of-Use）竞争条件。

当前 `readMission()` / `writeMission()` 均为同步操作，`atomicWriteFileSync`（write→tmp→rename）提供了单次写入原子性，但无法保护"读取→校验→写入"的整段临界区。

## 涉及文件

- `scripts/lib/fs-utils.ts` — 新增 `acquireMissionLock` / `withMissionLock` 函数
- `scripts/lib/mission-commit.ts` — 在 `commitMissionUpdate` 非 dryRun 写入区间使用 `withMissionLock`
- `scripts/file-lock.test.ts` — 新增文件锁单测

## 方案

### 锁机制：基于 mkdirSync 原子性

使用 `fs.mkdirSync(lockDir)` 创建 `.lock` 目录作为互斥锁。同一路径只有一个调用能成功，其余抛 EEXIST 错误，天然原子，无需额外系统调用。

锁目录路径：`<missionsDir>/<missionId>/.lock`

锁目录内写入 `holder.json` 记录持锁进程 PID 和获取时间，用于调试和过期检测。

### 关键参数

- `LOCK_TIMEOUT_MS = 10_000` — 获取锁超时 10 秒
- `LOCK_RETRY_INTERVAL_MS = 50` — 重试间隔 50ms
- 过期锁检测：holder.acquiredAt 超过 LOCK_TIMEOUT_MS 自动破锁

### API

```typescript
acquireMissionLock(missionsDir, missionId): LockHandle | null
withMissionLock<T>(missionsDir, missionId, fn: () => T): T | null
```

`withMissionLock` 确保 fn 执行完毕（无论正常或异常）后自动释放锁。

### commitMissionUpdate 改造

将"校验状态迁移 → 写入 mission.json → 发送通知 → 写入事件"这段关键区间整体包裹在 `withMissionLock` 内。dryRun 模式不需要加锁。
